# プロンプトテンプレート集 (docs/prompts/templates.md)

AIエージェントへの指示が曖昧な場合、手戻りや確認過多（パターン②）、都合の良い捏造計算や偽テスト（パターン③）が発生し、所要時間やトークン消費が数倍に膨らみます。
このテンプレート集は、5大受入基準（Definition of Input: DoI）を満たし、手戻りを防いで迅速完結（パターン①）させるための標準書式です。

---

## 1. 新機能追加・改修テンプレート

```markdown
### 目的
[何を実現したいかを1〜2文で記述]

### スコープと境界（DoI-1）
- 変更許可ファイル/ディレクトリ: [例: backend/services/scoring.py]
- 変更禁止領域: [例: 既存のDBスキーマ、frontend/配下]

### 入力と出力
- 入力データ: [例: 過去試合データ（match_datetime 以前のレコードのみ）]
- 期待する出力形式: [例: JSON形式、画面コンポーネント、特定関数の戻り値]

### ドメイン制約・エッジケース処理（DoI-2）
- 未来データ参照: 厳禁。イベント発生前のデータのみを使用すること。
- データ欠損時の扱い: [例: 数値を捏造せず、明示的に NaN を返すこと / 初出場選手は全体分布の中央値を適用すること]
- 端数・按分処理: [例: 複数問題にまたがる場合は問題数で均等割りにすること]

### 検証・完了条件（DoI-4）
- テスト要件: [例: 単に関数を呼ぶだけでなく、期待される戻り値の数値に対する assert を記述すること]
- 完了条件: [例: 単体テスト全件パス、型チェック通過]
```

## 2. データ集計・予測ロジック用テンプレート

```markdown
### 集計・予測要件
[算出したい指標や予測ロジックの内容]

### 対象データ境界（DoI-1, 2）
- 基準日時: [例: match_datetime（試合開始日時）]
- 除外対象: 確定スコア、最終順位、試合後スタッツ、勝敗フラグ

### 欠損値とスコアリングの制約（DoI-2）
- データが存在しない対象に対して、インデックス剰余（idx % 6 等）や固定値で数値を捏造しないこと。
- 過去データのない対象は、[明示的な欠損値 / 全体平均] を適用すること。

### 到達率・配線の検証（DoI-4）
- 新設テーブル・特徴量が末端関数に届いているか、実到達率（全対象に対する有効割合）をアサーションするテストコードを追加すること。
```

## 3. インフラ・CI/CD設定用テンプレート

```markdown
### 設定対象
[例: GitHub Actionsワークフロー / Terraform / Dockerfile]

### 事前調査の義務付け（DoI-3）
- 実装前に公式ドキュメントやリポジトリの仕様を調査し、`docs/references/` に技術メモを作成してください。
- 記憶や推測で権限・引数を指定せず、調査メモの記述に基づいて設定してください。

### 権限・リソース制約
- IAM権限: 最小権限原則を適用（ワイルドカードや過剰ロールは不可）。
- 起動性能: 起動処理は5秒以内に完了すること（ヘルスチェック前の全件DBスキャン禁止）。
- ビルド除外: `.dockerignore` を同時に更新し、ビルドコンテキストを最小化すること。
```

---

## 4. 完了確認・不具合修正用テンプレート

```markdown
### 確認対象の指定（DoI-1）
[「全部治ってるの？」は禁止。確認したい具体的な項目を列挙する]
- 確認項目1: [例: 選手詳細モーダルでの防御率表示]
- 確認項目2: [例: Cloud Run 起動時のヘルスチェック通過]

### 修正完了の判定基準（DoI-4）
- 単に修正コードを生成するだけでなく、エラーが再現していたテストがパスすることを確認すること。
- 修正による影響範囲（起動経路、依存ライブラリ）に副作用がないことを確かめること。
```
